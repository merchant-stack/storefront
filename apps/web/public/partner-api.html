Partner Integration Guide

How to integrate the RustSupply payment gateway into your platform. Your server creates a payment session, your user pays on a hosted form, and we notify your server with a signed webhook when the payment completes.

This document is the integration spec for a partner's server-side developer. You call the RustSupply gateway to accept card and regional payment-method deposits from your users, then receive an HMAC-signed webhook from us when a payment completes. Your buyers never leave a branded, hosted payment flow.

Architecture in 30 seconds

   Your platform (server)
        │
   (1) POST /api/merchant/sessions   (HMAC-signed)
        ▼
   RustSupply API
        │
   (2) returns checkout_url
        ▼
   You redirect the user's browser to the hosted payment form
        │
   (3) user pays (card / regional method)
        ▼
   RustSupply confirms PAID
        │
   (4) RustSupply POSTs an HMAC-signed webhook to YOUR endpoint
        ▼
   Your webhook handler verifies the signature and credits the user
        │
   (5) the user's browser is redirected back to your return_url
       (UX only — credit the user from the webhook in step 4, not the redirect)

Credentials we provide

  • MERCHANT_ID — your merchant identifier, e.g. m_yourbrand.
  • API_SECRET — 32-byte hex string. Used to HMAC-sign your requests to us.
  • WEBHOOK_SECRET — 32-byte hex string. Used to HMAC-sign our outbound webhooks to you, so you can verify they came from us.

Both secrets are server-side only. Never ship them to the browser.

What we need from you

  • Your webhook URL — where we POST signed payment events (e.g. https://your-domain.com/webhooks/rustsupply).
  • Your server's egress IP(s) — the public IPs your backend calls our API from. We allowlist them so even a leaked API_SECRET can't be used from an arbitrary IP. A single IP, a list, or a CIDR range all work. During initial integration we can leave the allowlist open if you don't have stable IPs yet.

Step 1 — Create a payment session

When a user starts a deposit/checkout on your side, your server makes one signed POST to RustSupply, then redirects the user's browser to the returned URL.

Request

POST https://api.rustsupply.com/api/merchant/sessions
Headers:
  Content-Type: application/json
  X-Merchant-Id: m_yourbrand
  X-Timestamp:   <unix-seconds>
  X-Nonce:       <16-32 hex chars, random per request>
  X-Signature:   <hex of HMAC-SHA256(API_SECRET, signing_string)>
Body:
  {
    "merchant_order_id": "ord_<your-internal-id>",
    "amount_minor": 5000,
    "currency": "USD",
    "return_url": "https://your-domain.com/checkout/<your-id>/done",
    "cancel_url": "https://your-domain.com/checkout/<your-id>/cancelled",
    "user_identifier": "<your-internal-user-id>",
    "metadata": { "any": "json you want echoed back in the webhook" }
  }

Required: merchant_order_id, amount_minor, currency, return_url. Optional: cancel_url, user_identifier, metadata.

Signing string

METHOD + "\n" + PATH + "\n" + TIMESTAMP + "\n" + NONCE + "\n" + sha256_hex(BODY)

That 5-line block (newline-separated, no trailing newline) is fed into HMAC-SHA256 with your API_SECRET. The hex result goes into X-Signature.

Response (201 Created)

{
  "session_id": "ord_xyz...",
  "checkout_url": "https://rustsupply.com/pay/ord_xyz...",
  "expires_at": "2026-01-01T14:30:00Z",
  "merchant_order_id": "ord_12345",
  "amount_minor": 5000,
  "currency": "USD"
}

Redirect the user's browser to checkout_url — they'll see the hosted payment form.

Idempotency

If your server retries the same merchant_order_id you get the same session back — never a duplicate. Use a new merchant_order_id only for a genuinely new payment.

Step 2 — Receive the success webhook

When the user pays, we POST a signed JSON payload to your webhook URL. You must verify the signature before crediting the user.

Headers we send

Content-Type: application/json
X-Event-Id: evt_xxxxxxxxxxxxxxxx
X-Timestamp: 1779700300
X-Signature: <hex HMAC-SHA256 over signing_string with WEBHOOK_SECRET>
User-Agent: RustSupply-Webhook/1.0

Signing string (different from the API request)

EVENT_ID + "." + TIMESTAMP + "." + RAW_BODY

Three dot-separated parts. Use the exact raw bytes of the body — don't re-parse/re-serialise before verifying.

Body

{
  "event": "session.paid",
  "event_id": "evt_xxxxxxxxxxxxxxxx",
  "session_id": "ord_xyz...",
  "merchant_order_id": "ord_12345",
  "amount_minor": 5000,
  "currency": "USD",
  "paid_at": "2026-01-01T14:25:00Z",
  "user_identifier": "<your-internal-user-id>",
  "metadata": { "...your original metadata echoed back..." }
}

Idempotency & retries

We retry failed deliveries on this schedule: 5 min, 15 min, 1h, 6h, 24h (6 attempts total). Store every event_id you've seen and skip duplicates. Return any 2xx with an empty body to confirm receipt; anything else (or a timeout > 10s) triggers a retry.

Sample code (Node.js)

Create a session

import crypto from 'node:crypto';

const API_URL = 'https://api.rustsupply.com/api/merchant/sessions';
const MERCHANT_ID = 'm_yourbrand';
const API_SECRET = process.env.RUSTSUPPLY_API_SECRET;

async function createSession({ orderId, amountUsd, userId }) {
  const body = JSON.stringify({
    merchant_order_id: orderId,
    amount_minor: Math.round(amountUsd * 100),
    currency: 'USD',
    return_url: `https://your-domain.com/checkout/${orderId}/done`,
    cancel_url: `https://your-domain.com/checkout/${orderId}/cancelled`,
    user_identifier: userId,
  });

  const timestamp = String(Math.floor(Date.now() / 1000));
  const nonce = crypto.randomBytes(16).toString('hex');
  const bodyHash = crypto.createHash('sha256').update(body, 'utf8').digest('hex');
  const stringToSign = ['POST', '/api/merchant/sessions', timestamp, nonce, bodyHash].join('\n');
  const signature = crypto.createHmac('sha256', API_SECRET).update(stringToSign).digest('hex');

  const res = await fetch(API_URL, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'X-Merchant-Id': MERCHANT_ID,
      'X-Timestamp': timestamp,
      'X-Nonce': nonce,
      'X-Signature': signature,
    },
    body,
  });
  if (!res.ok) throw new Error(`session create failed: ${res.status}`);
  return res.json(); // { session_id, checkout_url, expires_at, ... }
}

Webhook handler

import crypto from 'node:crypto';
import express from 'express';

const WEBHOOK_SECRET = process.env.RUSTSUPPLY_WEBHOOK_SECRET;
const seenEventIds = new Set(); // back this with Redis / DB in production

const app = express();

app.post('/webhooks/rustsupply', express.raw({ type: 'application/json' }), (req, res) => {
  const eventId = req.header('X-Event-Id');
  const timestamp = req.header('X-Timestamp');
  const signature = req.header('X-Signature');
  if (!eventId || !timestamp || !signature) return res.sendStatus(400);

  const drift = Math.abs(Math.floor(Date.now() / 1000) - Number(timestamp));
  if (!Number.isFinite(drift) || drift > 5 * 60) return res.sendStatus(400);

  const body = req.body.toString('utf8');
  const stringToSign = [eventId, timestamp, body].join('.');
  const expected = crypto.createHmac('sha256', WEBHOOK_SECRET).update(stringToSign).digest();
  const provided = Buffer.from(signature, 'hex');
  if (provided.length !== expected.length || !crypto.timingSafeEqual(provided, expected)) {
    return res.sendStatus(400);
  }

  if (seenEventIds.has(eventId)) return res.sendStatus(200);
  seenEventIds.add(eventId);

  const event = JSON.parse(body);
  if (event.event === 'session.paid') {
    creditUserBalance(event.user_identifier, event.amount_minor, event.session_id);
  }
  res.sendStatus(200);
});

Security checklist (your side)

  • Store secrets server-side only. Never expose them to the browser.
  • Verify the webhook signature before doing anything with the payload.
  • Check timestamp drift (±5 min) and reject duplicate event_ids.
  • Credit from the webhook, not the browser redirect — anyone can hit your return URL.
  • Idempotency at credit time — wrap the credit in a unique-key DB constraint.
  • Don't trust amounts from the browser — the webhook echoes the server-side amount you set at session creation.
